## 实现

- USB仍为1280×720 MJPEG@60，持续grab/retrieve原始JPEG，仅复制压缩字节到容量1的最新帧槽，取流线程不再每秒解码60次。
- 独立解码线程按消费请求工作，依据主循环实际计算时间（排除等待解码）与解码成本的滑动估计，在预计下一次取帧前准备一个最新帧；默认40FPS是解码频率上限，并非固定解码40次。主循环约26FPS时，实际解码也约26次。调度预测仅决定唤醒时间，不改变超时和陈旧帧检查。
- 同一个解码线程完成原有resize/letterbox/BGR→RGB，将原图、ModelImage、原始取流时间和frame_id一起交接。主线程推理与下一帧解码/预处理重叠；检测与pose仍共用同帧输入、并行运行各自context。
- 两种帧槽均只有最新一帧；cv::Mat引用计数保留正在使用的压缩/模型输入缓冲，原图在消费端仍clone，隔离后续绘图。移除解码生产端的全尺寸clone，保留必要所有权边界。
- 保留latest()轮询调用兼容、停止唤醒、故障停止、重新启动清空旧帧与计数器。capture_overwritten也统计解码前跳过的压缩帧，并不代表JPEG解码错误。相机无法返回有效JPEG或解码尺寸不符会停止采集，主程序沿原有错误/陈旧帧路径退出。

没有修改模型、640输入、归一化、阈值、NMS、检测core0/pose core1、相机曝光策略或机器人控制逻辑；没有部署此前超时的MPP硬解，也没有改成未经精度验证的INT8。

## 分项收益

诊断组profile_demand40.csv中，JPEG仍约9.66ms CPU/张，但调用由约60次/秒降为约26次/秒，累计单核等效约24.0%（此前分项约55.7%）。原始JPEG retrieve约0.076ms/次、复制约0.034ms/次。预处理约1.56ms移到解码线程；主线程vision总墙钟约37.96ms，循环约38.65ms。pose仍是主要NPU瓶颈，本轮没有缩短模型图本身的执行时间。

第一版固定30/40/60FPS解码也提升吞吐，但40FPS版本frame_age约35ms，故未作为默认部署。最终消费节奏调度将该项降至约22ms，同时CPU进一步降至约55%。初版全部对照数据保留在results/，正式默认为demand-results/所验证的调度方式。

## 时间戳与适用范围

旧路径timestamp位于JPEG解码完成之后；新路径位于压缩帧读取完成、解码之前。新frame_age包含解码及预处理等待，统计更保守；表中新旧frame_age不能直接当成相同口径比较，也不能据此宣称曝光到推理或显示延迟降低。两者都不是传感器曝光时间；现场运动画面与曝光到决策延迟仍未实测。

PERF inference_ms原先包含主线程预处理，现在预处理已在线程中完成，所以该字段也不能独立用来声称NPU提速。整体FPS、完整进程CPU与原始分项CSV才是本轮主要证据。

实际实时画面仍没有目标或有效安全区。当前数据覆盖双模型执行与采集稳定性，不能替代密集目标、有效区精度或机器人实地验收。若要求稳定超过30FPS，下一阶段仍需pose执行图优化和专项精度验证；本轮保留原模型精度路径。

4. 最终构建成功，22/22 CTest通过，git diff --check、bash -n和match_main.sh --check通过。FP16 pose既存非有限值问题未在本轮修复；位模式一致不等于问题消失。

## 使用与回退

正式启动器已经使用--async-capture，因此无需再增加CLI开关就会默认启用新路径。

```bash
# 回退为此前持续解码的采集路径，原生FP16输入优化仍保留
export RESCUE_CAPTURE_RAW_MJPEG=0
# 恢复本轮默认优化
unset RESCUE_CAPTURE_RAW_MJPEG
# 可选：修改解码频率上限，1..相机请求FPS；默认min(40, 相机请求FPS)
export RESCUE_CAPTURE_DECODE_FPS=40
```
