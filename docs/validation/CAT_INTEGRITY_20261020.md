## 恢复步骤与验收门槛

1. 具备现场条件后，优先将 eMMC 接到另一台可信且稳定的主机；也可使用独立、可信的 SD/USB 救援系统，但必须先验证执行镜像和修复的主机供电、内存稳定，不能在可疑内存上运行写入式修复。先按容量、分区、UUID 和挂载信息识别设备；设备名可能改变。保全原始介质镜像及恢复日志，有读错误时优先使用可续传的镜像恢复工具，避免反复全盘读写。
2. 在稳定救援主机上确认目标分区及其别名均未挂载，再优先对镜像副本检查、修复 EXT4，保留未修复原始镜像。在线根分区不满足条件；不得把在线 `fsck -n` 的结果当成可靠离线诊断。本批未执行任何 fsck。
3. 独立排查原板供电、内存与存储，用可信工具做内存诊断，并复查输入在不同读写阶段的完整性。一次摘要匹配或一次内存测试通过不足以排除此前 tmpfs 变化；若仍出现非预期字节变化，应继续排查或替换主机，停止应用验收。
4. 硬件、文件系统与输入稳定后，优先从可信系统镜像重建完整操作系统；若保留原系统，须用独立签名来源核验完整系统包及关键启动文件，并恢复所有不一致项。重新建立工具链、相关依赖及实际读出字节的完整性；只替换 `cc1plus` 不能证明整个系统已恢复。复核模型、RKNN 库、标定和启动资源；恢复部署文件不等于迁移到重构程序。
5. 最后从本机可信冻结源码全新完整构建，核对构建前后源码及资源摘要、内核错误和工具链。运行完整 ARM CTest、显式精确 ARM 基线、7 项原/新应用对照及新批相机串并行、信号退出、无效设备和资源重开验证。全部记录完成前，保持“健康 ARM 最终验收待补”。

本机既有回归仍为遥测 ON 41/41、OFF 40/40；本批没有业务代码修改，也未把这些历史结果重记为本批测试。原持久夹具和精确 ARM 补充夹具摘要保持不变。
