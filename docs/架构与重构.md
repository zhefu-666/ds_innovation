# 架构与重构

当前工程由采集、RKNN推理、观测与几何处理、任务状态机、机构及运动通信、遥测发布组成。正式比赛代码与独立演示副本需要明确区分；本轮已将校赛构建来源的差异收拢到项目，尚未统一演示副本。

下面保留原总体方案与构建规格，作为设计依据，不表示所有模块均已实现或验收。特别是历史ToF假设、模块命名和实施顺序不能作为当前硬件/代码事实；当前入口和协议以专门文档为准。

## INTELLIGENT_RESCUE_OVERALL_PLAN

### 智能救援机器人总体方案

#### 1. 项目目标

本方案面向智能救援比赛，目标是在约 3 m × 3 m 的场地内，使用 RK3588S 上位机、单目 USB 摄像头、底盘 IMU 和四路 ToF，实现救援目标搜索、识别、地面推送、正确安全区投送和往复运行。

比赛规则的关键约束：

- 普通物资、核心物资和伤员是双方公共救援目标。
- 初赛目标包括绿色普通物资、黑色核心物资、橘色伤员和浅蓝色危险目标。
- 必须先将至少一个普通物资送入本队物资区，才能转运核心物资和伤员。
- 禁止使用机械臂抓取目标，禁止将目标放在机器人上。
- 物资一次最多转运 3 个；伤员必须单独转运，每次 1 个。
- 危险目标不能移出场地，也不能进入安全区，否则本轮比赛结束。
- 普通物资、核心物资、伤员分别为 5、10、15 分；放错位置每个扣 10 分。
- 机器人进入对方安全区会扣分，因此安全区边界必须被视为禁入区域。

本方案的第一阶段目标不是一次转运最多目标，而是稳定完成：

> 从任意出发区找到一个绿色普通物资，将其安全推送至本队物资放置区，确认有效送达后返回搜索区域。

#### 2. 硬件与软件总体架构

### 2.1 硬件配置

- 计算平台：RK3588S
- 主视觉：720p、60 FPS USB 单目摄像头
- 姿态与航向：底盘 IMU
- 近场测距与避障：四路 ToF
- 底盘执行：下位机控制电机、推送机构和传感器
- 通信：上位机与下位机之间使用 UART；如底盘已有 CAN，也可将实时底盘控制改为 CAN
- 如果底盘带编码器，建议接入；编码器可以显著改善巡航距离和返回动作

### 2.2 软件分工

| 模块 | 主要职责 |
|---|---|
| RK3588S 上位机 | 图像采集、目标识别、目标跟踪、安全区识别、任务决策、局部路径规划 |
| 单目视觉 | 识别目标类别、危险物、安全区结构和隔板；估计目标相对位置 |
| IMU | 航向保持、转角控制、越障姿态判断、碰撞和失控检测 |
| 四路 ToF | 近场障碍检测、停车、倒车防撞、转弯侧向防护 |
| 下位机 | 电机闭环、传感器实时读取、限速、超时停车和急停 |
| UART/CAN 协议 | 传递运动目标、任务状态、传感器数据和故障状态 |

上位机负责“看、想、选目标、规划”；下位机负责“快速执行和安全停车”。

#### 3. 视觉识别方案

### 3.1 建议的模型类别

当前项目仍使用 `Red_Ball`、`Blue_Ball`、`Yellow_Ball` 等旧类别，需要重新训练模型。建议类别为：

```text
ordinary_supply       # 绿色普通物资
core_supply           # 黑色核心物资
injured_person        # 橘色伤员目标
dangerous_object      # 浅蓝色危险目标
red_safe_zone         # 红色安全区整体
blue_safe_zone        # 蓝色安全区整体
safe_zone_divider     # 安全区中间隔板，可选
robot                 # 对方机器人，可选
```

物资区和伤员区外观、颜色基本一致，不能把它们作为完全独立的颜色分类问题。正确方法是：

> 识别安全区整体外框和中间隔板，再通过子区域的固定空间位置确定物资区或伤员区。

### 3.2 检测与实例分割

目标紧挨时，普通 YOLO 检测框可能重叠，容易将两个目标看成一个。推荐使用轻量实例分割模型：

```text
best.pt → best.onnx → best.rknn
```

输出每个实例的：

- 类别；
- 置信度；
- 外接框；
- mask；
- 轮廓；
- 跟踪编号。

如果 RK3588S 算力或开发周期有限，可以先使用检测模型验证流程，再切换到 YOLO-seg 或其他轻量实例分割模型。

### 3.3 颜色和形状复核

由于比赛文件明确说明实际颜色存在色差，颜色不能作为唯一依据，但可以作为二次检查：

- 在实例 mask 内计算 HSV/Lab 主色比例；
- 检查绿色、橘色、浅蓝色和黑色区域；
- 结合外接框长宽比、面积和轮廓形状；
- 对黑色四面体使用轮廓和多帧信息，不能仅凭亮度判断；
- 模型类别、颜色和形状冲突时，标记为不确定并停车复核。

危险目标采用保守策略：只要模型、颜色或几何特征中任一项提示危险，就按照危险目标处理。

### 3.4 目标跟踪

目标检测结果需要通过 SORT、ByteTrack 或自定义最近邻跟踪保持目标 ID。跟踪信息至少包括：

```cpp
struct TargetObservation {
    int track_id;
    TargetType type;
    float x_m;              // 车体前向距离
    float y_m;              // 车体横向位置
    float confidence;
    uint64_t timestamp;
    bool is_occluded;
};
```

不能把“某个检测框变大”或“目标消失”直接当成目标已经被移动或送达。

#### 4. 单目定位方案

### 4.1 地面标定

场地主要是平面，单目相机可以通过地面单应性估计目标相对位置：

1. 标定相机内参和畸变；
2. 固定相机高度、俯角和横向安装位置；
3. 在地面布置多个已知距离的标定点；
4. 建立图像坐标到地面坐标的映射；
5. 使用目标框底边中心或目标 mask 的接地边缘作为地面点；
6. 转换到车体坐标，输出前向距离和左右偏移。

目标框中心不能直接作为地面点，因为它通常位于物体表面上方。

### 4.2 IMU 融合

IMU 用于：

- 保持推送方向；.0
- 执行 90° 和 180°转向；
- 判断越过减速带后车体是否稳定；
- 检测碰撞或异常姿态；
- 对短时间视觉丢失进行航向保持。

IMU 不适合单独通过加速度积分完成长期位置定位。若有编码器，应采用：

```text
编码器短程里程计 + IMU 航向 + 视觉相对位置修正
```

### 4.3 ToF 融合

ToF 主要用于近场安全，不负责识别目标类别。四个 ToF 建议布置为：

- 左前：左侧前方障碍；
- 右前：右侧前方障碍；
- 左后：倒车和左后侧防撞；
- 右后：倒车和右后侧防撞。

ToF 距离建议分为安全、减速、停车三个等级，实际阈值由车体宽度、机构尺寸和制动距离标定。推送时前向 ToF 可能测到正在推送的目标，需要结合任务状态处理；左右和后方 ToF 仍保持安全保护。

#### 5. 路线规划方案

#### 5.1 不做完整全局 SLAM 的原因

场地尺寸较小、结构相对固定，但目标位置现场可能变化，对方机器人会造成动态干扰。单目 SLAM 还会受到：

- 地面纹理不足；
- 运动模糊；
- 目标和障碍移动；
- 单目尺度不稳定；
- 减速带引起的姿态变化。

因此第一版不建议投入完整高精度全场 SLAM，而采用“区域拓扑 + 局部规划 + 视觉重新定位”。

### 5.2 功能区域

建议在程序中定义：

```text
START_ZONE              出发区
SEARCH_ZONE             中央搜索区
SUPPLY_OBSERVE_ZONE     本队物资区前方观察区
INJURED_OBSERVE_ZONE    本队伤员区前方观察区
BACKUP_OBSERVE_ZONE     备用观察区
```

车辆每次只执行短距离动作，到达阶段性位置后重新观察。若有编码器，可以记录粗略位置；没有编码器时依靠视觉重新看到目标或安全区完成阶段切换。

### 5.3 目标接近点

目标位置为 `T`，目标投送点为 `G`，机器人应先到目标背后的接近点 `A`：

```text
A = T - d × normalize(G - T)
```

其中 `d` 为机构前端到目标的安全预留距离，需要实车标定。

执行过程：

```text
车辆 → 接近点 A → 调整航向 → 低速建立推送接触 → 沿 G 方向推送
```

不建议看到目标后直接正面接近，再带着目标寻找安全区。推送前应先确定目标和目的地的方向关系。

### 5.4 局部候选路径

对每个目标生成：

```text
直达路线
左绕路线
右绕路线
换观察点路线
```

对每条路线检查：

- 车体轮廓；
- 推送机构轮廓；
- 被推目标轮廓；
- 危险目标膨胀区；
- 其他目标；
- 对方机器人；
- ToF 实时障碍。

危险物是硬约束，任何候选路径与危险区重叠都必须淘汰。带目标转弯的风险高于空车绕行，第一版优先直线推送或换目标。

#### 6. 安全区识别与正确投送

### 6.1 安全区几何识别

不要训练模型直接判断“物资放置区”或“伤员放置区”。建议识别：

- 安全区整体外框；
- 四个角点；
- 中间隔板或分界线；
- 安全区朝向；
- 安全区相对车体的位置。

将安全区变换到标准局部坐标：

```text
标准安全区坐标：
左子区域：u ∈ [0, 0.5]
右子区域：u ∈ [0.5, 1.0]
```

通过配置文件确定物资区和伤员区的对应关系：

```text
红色安全区：物资区 = 左/右，伤员区 = 右/左
蓝色安全区：物资区 = 左/右，伤员区 = 右/左
```

红蓝安全区的子区域顺序必须依据正式场地和现场方向确认，不能凭图像中的左右默认。

### 6.2 目标类别到子区域的映射

```cpp
if (target.type == ORDINARY_SUPPLY || target.type == CORE_SUPPLY) {
    destination = safe_zone.supply_subzone;
} else if (target.type == INJURED_PERSON) {
    destination = safe_zone.injured_subzone;
} else {
    reject_target();
}
```

安全区颜色只用于确认是否为本队安全区；目标类别决定投送到物资区还是伤员区。

### 6.3 投送点计算

每个子区域需要设置内部投送点，而不是使用整个安全区中心。投送点应：

- 远离中间隔板；
- 远离外框和围栏；
- 远离入口边缘；
- 为目标尺寸、推送误差和惯性留出余量。

伤员目标尺寸较长，投送安全区域应比 40 mm 方块更小，不能使用统一投送点。

### 6.4 禁投区域

将中间隔板和安全区边界设置为禁投缓冲区：

```text
有效投送区域 = 子区域几何范围
              - 目标外接尺寸
              - 边界安全余量
              - 视觉和控制误差
```

目标中心进入子区域并不等于有效送达。目标外轮廓也必须没有压住隔板、围栏或错误子区域。

### 6.5 安全区被遮挡时

如果隔板、外框或子区域关系不可见：

1. 停车等待图像稳定；
2. 后退 10～20 cm；
3. 小角度转动或横向改变观察位置；
4. 重新识别整体外框和隔板；
5. 连续多帧确认布局；
6. 仍无法确认时放弃本次投送。

不能用安全区颜色中心代替隔板位置。

#### 7. 任务状态机

当前项目的“寻找球体—抓取—寻找安全区—放球”状态机需要改为：

```text
WAIT_START
DEPART
SEARCH_TARGET
SELECT_TARGET
APPROACH_TARGET
ALIGN_PUSH
PUSH_TARGET
NAVIGATE_DROP_ZONE
IDENTIFY_DROP_SUBZONE
ALIGN_DROP
RELEASE_OR_EXIT
VERIFY_DELIVERY
RETURN_SEARCH
EMERGENCY_STOP
```

### 关键状态转移

- `WAIT_START`：停车等待统一开始指令。
- `DEPART`：低速越过减速带，IMU 确认姿态稳定。
- `SEARCH_TARGET`：巡航或原地扫描。
- `SELECT_TARGET`：初次送达前只选择普通绿色物资；危险目标永远排除。
- `APPROACH_TARGET`：计算目标背后接近点。
- `ALIGN_PUSH`：用视觉横向误差和 IMU 航向对准推送方向。
- `PUSH_TARGET`：低速直线或小幅修正推送。
- `NAVIGATE_DROP_ZONE`：前往本队安全区观察区。
- `IDENTIFY_DROP_SUBZONE`：识别整体安全区、隔板和正确子区域。
- `ALIGN_DROP`：将目标和投送方向对准目标子区域内部。
- `VERIFY_DELIVERY`：确认目标在正确子区域稳定存在。
- `RETURN_SEARCH`：退出安全区并返回搜索区域。
- `EMERGENCY_STOP`：ToF、IMU、视觉、通信任一安全条件触发时停车。

建议第一版物资一次只推送 1 个。确认单个普通物资成功后，再逐步加入核心物资、单个伤员和多物资批量转运。

#### 8. 有效送达确认

送达判断必须是一个独立状态，不能用固定前冲时间、动作完成或目标短暂消失代替。

建议同时满足：

1. 目标类别可信；
2. 目标 mask 或轮廓进入正确子区域；
3. 目标外轮廓没有越过隔板或外框；
4. 连续 8～15 帧位置稳定；
5. 机器人后退脱离接触后，目标仍留在区域内；
6. 目标没有被推出安全区或落在围栏上。

建议流程：

```text
目标进入子区域
→ 停止推进
→ 后退约 0.15～0.25 m
→ 观察约 0.5～1.0 s
→ 连续多帧确认
→ 记录有效送达
```

只有普通物资满足有效送达条件，才设置：

```cpp
first_supply_delivered = true;
```

此后才允许选择核心物资和伤员。

#### 9. 上位机和下位机通信

当前项目主要发送两路电机速度和舵机角度，无法完整表达新的任务控制需求。建议扩展消息内容。

### 9.1 上位机发送

```text
协议版本
指令序号
任务状态
控制模式
目标线速度
目标角速度或目标航向
速度上限
停车/急停标志
指令有效时间
CRC
```

### 9.2 下位机返回

```text
指令序号
执行状态
IMU yaw/pitch/roll
四路 ToF 距离
ToF 有效标志
编码器里程计（如有）
电机故障
通信状态
```

### 9.3 安全要求

- 上位机控制指令建议 50 Hz；
- 电控底盘闭环建议 100 Hz；
- IMU、ToF 建议 50～100 Hz；
- 指令超过约 200 ms 未更新，下位机自动停车；
- 指令必须带序号，旧指令不能重复执行；
- 急停由下位机直接处理，不等待视觉线程；
- 推送状态下前向 ToF需要结合当前目标处理，左右后方 ToF保持防护；
- 视觉数据带时间戳，过期数据不得继续控制车辆。

#### 10. RK3588S 运行建议

当前 `src/yolo_detector.cpp` 使用 OpenCV DNN 读取 ONNX，适合开发机和初期联调。正式部署到 RK3588S，建议使用 NPU：

```text
best.pt
  → best.onnx
  → best.rknn
  → RK3588S NPU 推理
```

建议保留两种后端：

```text
YoloOnnxDetector   # 开发与调试
YoloRknnDetector   # RK3588S 正式运行
```

推荐线程划分：

```text
相机采集线程：60 FPS
YOLO 检测线程：15～25 FPS
目标跟踪线程：30～60 FPS
IMU/ToF 读取线程：50～100 Hz
控制线程：50～100 Hz
任务状态机：独立线程或固定周期循环
```

不要要求 YOLO 对 720p 60 FPS 的每一帧都推理。检测与跟踪分离可以降低延迟，提高控制稳定性。

#### 13. 重要注意事项

### 13.1 规则风险

- 禁止使用机械臂抓取，机构必须采用地面推送或规则允许的其他方式；
- 不能把目标放到机器人上；
- 危险物绝不能被推离场地或送入安全区；
- 不要进入对方安全区；
- 物资区和伤员区必须依据位置关系区分，不能只靠颜色；
- 目标放在隔板、围栏或错误子区域会扣分。

### 13.2 视觉风险

- 720p 60 FPS 是采集帧率，不等于 YOLO 推理帧率；
- 目标紧挨时必须考虑实例分割或传统分割复核；
- 颜色存在色差，固定 HSV 阈值不能作为唯一识别条件；
- 远距离目标定位误差较大，近距离必须重新定位；
- 车体越过减速带时，固定地面映射会失准；
- 隔板被遮挡时禁止盲目投送；
- 视觉数据过期时必须停车，而不是继续使用旧坐标。

### 13.3 传感器和控制风险

- IMU 不能单独完成长期位置定位；
- 单个 ToF 不能识别目标类别，也不能覆盖所有方向；
- ToF 可能测到正在推送的目标，必须按任务状态区分；
- 电控必须具备通信超时停车和急停优先级；
- 视觉控制与电控位置控制不能同时抢占底盘；
- 推送状态速度必须低于空车巡航速度；
- 目标丢失、危险物接近、姿态异常、通信异常都要进入停车复核。

### 13.4 比赛现场风险

- 安全区和目标的位置可能与训练场景不同；
- 场地围栏不是精确定位基准；
- 实际目标颜色会有色差；
- 两台机器人可能相互遮挡和干扰；
- 目标被碰撞后可能改变位置，不能长期依赖赛前地图；
- 赛前应快速采集安全区方向、出发区和主要障碍信息，但不能依赖复杂人工操作。

#### 14. 最终推荐方案

最终采用以下闭环：

```text
等待开始
→ 越障出发
→ 区域巡航和视觉扫描
→ 选择允许且路径安全的目标
→ 识别危险目标并膨胀安全区
→ 计算目标背后接近点
→ IMU 保持航向，视觉完成局部对准
→ ToF 实时防撞
→ 单目标低速推送
→ 前往本队安全区观察位置
→ 识别安全区整体外框和中间隔板
→ 根据目标类型确定物资区或伤员区
→ 计算子区域内部投送点
→ 低速推入并避开隔板、围栏
→ 后退脱离
→ 多帧确认目标稳定留在正确子区域
→ 记录有效送达
→ 返回搜索区域
```

方案的核心原则是：

1. **模型识别目标类别，几何关系识别安全区子区域。**
2. **危险目标识别和避让是硬约束。**
3. **视觉负责决策，IMU 和 ToF负责实时安全闭环。**
4. **不依赖单目相机直接提供绝对位置，而利用地面标定和短程传感器融合。**
5. **先稳定完成单个普通物资的有效送达，再增加高分目标和批量转运。**

#### 5. 模块拆分

### 5.1 `camera_capture.*`

- 打开 1280×720/60 FPS 相机。
- 独立采集线程，使用最新帧策略，不能阻塞控制线程。
- 记录帧时间戳和丢帧计数。

### 5.2 `detector.*`

- 保留现有 `YoloOnnxDetector` 作为开发后端。
- 新增 `YoloRknnDetector` 接口占位或实现。
- 统一输出 `SegDetection`。
- 支持检测间隔 15～25 Hz，跟踪 30～60 Hz。

### 5.3 `tracker.*`

- 使用 ByteTrack、SORT 或轻量最近邻跟踪。
- 目标类别变化、遮挡、重新出现时不得随意复用 track_id。
- 跟踪丢失超过阈值进入停车复核。

### 5.4 `camera_calibration.*`

- 读取相机内参和畸变参数。
- 读取地面单应矩阵。
- 将目标接地点转换为车体坐标。
- IMU pitch/roll 超过阈值时降低定位可信度。

### 5.5 `safe_zone_pose.*`

- 检测安全区外框角点、隔板点和可选围栏上下边缘。
- 使用 `solvePnPRansac` 求安全区位姿。
- 输出重投影误差和 FRONT/SIDE/PARTIAL 状态。
- 角点不足、误差过大或姿态跳变时返回无效。

### 5.6 `zone_layout.*`

使用配置定义安全区子区域语义，不通过图像左右猜测：

```cpp
struct ZoneLayout {
    std::string zone_label;
    enum Side { LEFT, RIGHT } supply_side;
    enum Side injured_side;
    float field_heading_deg;
};
```

只有安全区完整且朝向已知时，才能将目标类别映射到具体子区。

### 5.7 `planner.*`

- 维护区域状态：START、CENTER、OBSERVE、DROP、UNKNOWN。
- 根据目标位置 `T`、投送点 `G` 计算接近点 `A`：

```text
A = T - d × normalize(G - T)
```

- 生成直达、左绕、右绕、换观察点候选路线。
- 检查车体、机构、目标和危险物膨胀区。
- 危险物碰撞风险是硬约束。
- 不要求第一版实现完整 SLAM。

### 5.8 `sensor_fusion.*`

- 合并视觉、IMU、ToF、编码器数据。
- IMU 用于航向保持和越障稳定判断。
- ToF 用于近场减速、停车和倒车防撞。
- ToF 触发安全停车优先级高于普通视觉运动命令。

### 5.9 `rescue_state_machine.*`

实现以下状态：

```text
WAIT_START
DEPART
SEARCH_TARGET
SELECT_TARGET
APPROACH_TARGET
ALIGN_PUSH
PUSH_TARGET
NAVIGATE_DROP_ZONE
IDENTIFY_DROP_SUBZONE
ALIGN_DROP
VERIFY_DELIVERY
RETURN_SEARCH
RECOVERY_SEARCH
EMERGENCY_STOP
```

状态机必须非阻塞；禁止使用长时间 sleep 阻塞暂停、ToF 和急停处理。

#### 6. 安全区投送算法

### 6.1 识别

```text
检测安全区整体
→ 提取外框和隔板
→ PnP 解算位姿
→ 判断是否正面观察
→ 侧面/局部视角移动到正面观察点
```

侧面检测只能表示“发现安全区”，不能直接投送。

### 6.2 子区选择

```text
ordinary_supply/core_supply → supply_side
injured_person              → injured_side
dangerous_object            → reject
```

### 6.3 投送确认

```text
目标进入指定子区
→ 停止推进
→ 低速倒退 0.15～0.25 m
→ 重新 PnP 和目标定位
→ 转换到安全区坐标系
→ 比较倒退前后目标相对位置
→ 连续 8～15 帧确认
```

有效送达必须满足：

- 目标整体在正确子区；
- 目标不跨隔板；
- 目标不压住围栏或边界；
- 机器人已脱离接触；
- 目标相对安全区位置稳定。

#### 7. 巡航和恢复

不使用无限固定路线。定义至少：

```text
中心观察点
左侧观察点
右侧观察点
备用观察点
```

每个观察点：

```text
停车 → 图像稳定 → 原地扫描 -45° 到 +45° → 更新目标列表
```

安全区或目标丢失：

```text
停车
→ 保持最后有效 IMU 航向
→ 短距离回退/回到上一个观察点
→ 扇区扫描
→ 仍失败则回到中心区域
→ 设置位置 UNKNOWN 并重新规划
```

#### 8. 通信要求

上位机发送：

```text
版本、序号、状态、模式、速度、目标航向、速度上限、急停、有效时间、CRC
```

下位机返回：

```text
序号、执行状态、IMU、四路 ToF、编码器、故障、通信状态
```

安全约束：

- 控制命令 50 Hz；
- 下位机闭环 100 Hz；
- 超过 200 ms 未收到新命令自动停车；

- 旧序号命令不得重放；

#### 1. 不可违反的规则

来源：《2027 年中国大学生工创实践与创新能力大赛 智能+工程创新赛道 竞赛命题解析》第 3 页。

由此推出四条硬性设计约束，任何一条被破坏都必须视为需求失败：

1. **单向**。只从机器人推数据出去，绝不接受任何输入。实现层面必须让反向通道不存在，而不是靠"我们不去点它"。

4. **可审计**。必须能向裁判一句话说明并当场展示代码：发布端只调用 `log()`，没有任何订阅/回调/服务注册。

### 1.1 闭环反向通道的具体关法

```cpp
enum class WebSocketServerCapabilities : uint8_t {
  None = 0,
  ClientPublish     = 1 << 0,  // 允许客户端向服务端发数据 —— 禁止
  ConnectionGraph   = 1 << 1,
  Parameters        = 1 << 2,  // 允许客户端读写参数 —— 禁止
  Time              = 1 << 3,
  Services          = 1 << 4,  // 允许客户端调用服务 —— 禁止
  Assets            = 1 << 5,
  PlaybackControl   = 1 << 6,  // 允许客户端控制播放 —— 禁止
};
```

`WebSocketServerOptions::capabilities` 保持默认 `None`。**不要注册**以下任何一项（名字均以 `cpp/foxglove/include/foxglove/websocket.hpp` 实际定义为准）：

```text

WebSocketServerOptions::callbacks.onMessageData            // 需 ClientPublish，客户端发来的数据
WebSocketServerOptions::callbacks.onClientUnadvertise      // 需 ClientPublish
```

`onSubscribe` / `onUnsubscribe` 是可选的只读观测回调，仅在需要统计客户端连接数时使用，不影响单向性。

#### 4. 依赖与构建

新增依赖：`foxglove/foxglove-sdk`（MIT，C++ 部分在 `cpp/`，是对 `c/` 库的上层封装）。

关键事实：

- C++ SDK 是 C 库的 wrapper，**必须先构建并链接 `c/` 库**，并把生成的 includes 加入头文件搜索路径（见 `cpp/README.md`）。
- 依赖默认从本机包管理器查找，找不到时经 FetchContent 从源码构建，由 `USE_PACKAGE_MANAGER_DEPENDENCIES` 控制（默认 `ON`）。在 RK3588S 上源码构建 nlohmann_json / Catch2 很慢且吃内存，**建议在本机或 CI 上交叉编译好再拷到板子**。
- 头文件内嵌了一份 tl-expected 的 `expected.hpp`。
- 官方示例 `cpp/examples/rgb-camera-visualization/main.cpp`（146 行）是最小可用模板，但**它用的是 `RawImageChannel`，按第 7 节必须换掉**。

CMake 方面新增可执行目标或静态库用于发布模块，并保持 `-DBUILD_TESTING=ON` 下现有 `ctest` 全部通过。发布模块必须能在**不链接 SDK** 时通过编译开关整体关闭：

```cmake
option(RESCUE_ENABLE_TELEMETRY "Build telemetry publisher" OFF)
```

默认 `OFF`，比赛安全版本可完全不带该模块构建。

#### 5. 通道映射

同一份数据同时进网络和进磁盘，靠 SDK 的 sink 机制实现：`Context` 关联日志与 sink，`WebSocketServer` 和 `McapWriter` 都是 sink，而 `log()` 的 `sink_id` 省略时**消息会发往所有 sink**。因此只需创建一次通道，网络与录制自动同时生效。

| 通道 topic | 消息类型 | 数据源 | 客户端面板 |
|---|---|---|---|
| `/camera/image` | `CompressedImage` | `CameraCapture::latest()` 缩放后 JPEG | Image |
| `/detections` | `ImageAnnotations` | `IDetector` + `Tracker` | 叠加在 Image 上 |
| `/fsm/state` | `KeyValuePair` | `RescueStateMachine` | Plot / Raw Messages |
| `/fsm/events` | `Log` | 状态转移事件 | Log |
| `/sensors/imu` | `KeyValuePair` | `SensorState` yaw/pitch/roll | Plot |
| `/sensors/tof` | `KeyValuePair` | `SensorState` 四路 ToF | Plot |
| `/cmd/motion` | `KeyValuePair` | `MotionCommand` | Plot |
| `/safezone/pose` | `FrameTransform` | `SafeZonePose` | 3D |
| `/camera/calibration` | `CameraCalibration` | 标定文件 | Image 去畸变 |

统一 frame_id 约定，避免客户端坐标错乱：

```text
camera_optical   相机光心，+x 右 +y 下 +z 入平面（CompressedImage 规定）
base_link        车体
field            场地
zone             安全区局部
```

`ImageAnnotations` / `KeyValuePair` / `FrameTransform` / `CameraCalibration` 的具体结构体字段以 SDK 头文件为准，实施时先读 `cpp/foxglove/include/foxglove/messages.hpp`，**不要凭记忆写字段名**。

#### 6. 发布模块设计

新增 `include/rescue/telemetry_publisher.hpp` 与 `src/telemetry_publisher.cpp`。

```cpp
namespace rescue {

struct TelemetryOptions {
    std::string host = "0.0.0.0";      // 必须 0.0.0.0，见下
    uint16_t port = 8765;
    std::string mcap_path;             // 空字符串则不录制
    int image_publish_fps = 10;        // 与视觉帧率解耦
    int image_width = 640;
    int image_height = 480;
    int jpeg_quality = 70;
    bool publish_images = true;
};

class TelemetryPublisher {
public:
    static std::unique_ptr<TelemetryPublisher> create(const TelemetryOptions& options);
    ~TelemetryPublisher();

    // 全部非阻塞，内部只做入队/覆盖，绝不等待网络
    void publishFrame(const cv::Mat& bgr, uint64_t timestamp_us);
    void publishDetections(const std::vector<SegDetection>& detections, uint64_t timestamp_us);
    void publishState(const std::string& state_name, uint64_t timestamp_us);
    void publishEvent(const std::string& state, const std::string& message, uint64_t timestamp_us);
    void publishSensors(const SensorState& sensors);
    void publishMotion(const MotionCommand& command, uint64_t timestamp_us);
    void publishSafeZone(const SafeZonePose& pose, uint64_t timestamp_us);
};

} // namespace rescue
```

实现要求：

- **独立发布线程**。所有 `publish*()` 只把数据放进内部缓冲并返回，真正的编码、序列化和 `log()` 调用在发布线程里做。主循环调用 `publish*()` 的耗时必须是常数级且极小。
- **图像最新帧覆盖**。缓冲只保留最新一帧，发布线程取走即清空；来不及发的帧直接丢弃并累加一个计数，通过 `/fsm/state` 暴露 `dropped_publish_frames`，便于判断是不是网络拖累了链路。
- **结构化数据不丢**。检测、状态、传感器是低带宽高价值数据，允许排队但必须限长（建议 256 条上限），超出丢最旧。
- **编码在发布线程做**。`cv::resize` + `cv::imencode(".jpg", ...)` 放在发布线程，不要在主循环做。
- **帧率解耦**。视觉推理按 `config/rescue.yaml` 的 `detect_interval` 照常跑，图像只按 `image_publish_fps` 往外发。两者互不影响。
- **异常不外抛**。发布线程内任何异常都只记录并继续，绝不终止进程、绝不影响控制。
- `host` 必须设成 `0.0.0.0`。官方示例里写的是 `127.0.0.1`，那样笔记本连不上。

### 6.1 发布线程伪代码

```text
loop:
    if stop_requested: break
    sleep_until(next_tick)                     # 固定 image_publish_fps 节拍
    if images_enabled:
        frame = grab_latest_frame()            # 无新帧则跳过
        if frame:
            small = resize(frame, 640x480)
            ok, buf = imencode(".jpg", small, quality=70)
            if ok:
                msg.data = as_bytes(buf); msg.format = "jpeg"
                msg.timestamp = to_timestamp(frame.timestamp_us)
                msg.frame_id = "camera_optical"
                image_channel.log(msg)
    drain_structured_queues()                  # 检测/状态/传感器/运动
```

#### 7. 带宽与性能要求

**这是本方案最容易失败的地方，不要跳过。**

`RawImage` 是未压缩原始帧。720p BGR8 单帧字节数：

```text
1280 × 720 × 3 = 2,764,800 B ≈ 2.64 MiB
```

| 方案 | 单帧/单秒带宽 | 弱板 CPU | 结论 |
|---|---:|---|---|
| `RawImage` 720p @60fps | ≈ 158 MiB/s | 低（但网络爆炸） | **禁用** |
| `RawImage` 720p @30fps | ≈ 79 MiB/s | 低 | **禁用** |
| `CompressedImage` JPEG 720p q70 @10fps | ≈ 0.8–1.5 MiB/s | 中 | 可用 |
| `CompressedImage` JPEG 640×480 q70 @10fps | ≈ 0.3–0.5 MiB/s | 低 | **推荐起点** |
| `CompressedVideo` H.264 硬编 720p @30fps | ≈ 0.25–0.5 MiB/s | 极低 | 进阶 |

要求：

1. 一律使用 `CompressedImageChannel`，**禁止** `RawImageChannel`。这是官方示例与本规格最大的差异点，实施时务必确认没有沿用示例的 `RawImageChannel`。
2. 起点参数：640×480、JPEG 质量 70、10 fps。跑通后可按实测调整。
3. 图像缩放在发布线程做，不要降低相机采集分辨率（视觉推理仍需要 720p 输入）。
4. `CompressedVideoChannel` + RK3588S 硬件编码器（rockchip mpp）作为第二阶段可选优化。**先不要做**，JPEG 路径没跑通之前不要引入 mpp 的时间戳对齐复杂度。
5. 必须实测并记录：开启/关闭遥测两种情况下的状态机帧率差异。若状态机帧率下降超过 5%，视为需求失败，回到第 6 节检查是否真的做到了非阻塞。

#### 8. 录制（MCAP）

`McapWriter` 与 `WebSocketServer` 同为 sink，创建两者即可让同一批通道同时进网络和进磁盘：

```cpp
foxglove::McapWriterOptions mcap_options;
mcap_options.path = options.mcap_path;
mcap_options.compression = foxglove::McapCompression::Zstd;   // 默认
auto writer = foxglove::McapWriter::create(mcap_options).value();
```

要求：

- 录制路径带时间戳，单场一个文件，避免跨场比赛混在一起。
- 录制开启时用 `sink_channel_filter` 排除 `/camera/image`，或把图像录制帧率再降一档，避免 eMMC 写入压力。**图像不是复盘的必要条件，状态和传感器才是。**
- 退出时调用 `flush()` 与 `close()`，确保文件可读。
- MCAP 文件落地后可用本机 Lichtblick 直接打开回放，不依赖机器人。
